# Требования к настройкам слежения за VPN (AntiSpyVpnWatchService)

Запрос пользователя 10.08.2026: «весь этот функционал должен в настройках регулироваться, вдруг у меня раздельное туннелирование и уведомления приходить не будут, когда могли бы».

## Что есть сейчас

`AntiSpyVpnWatchService` следит за поднятием VPN и по этому событию пакетно морозит приложения рабочего профиля по списку автозаморозки основного профиля.

**Настройки для этого нет.** Проверено: в `res/xml/preferences_settings.xml` нет ни одного пункта, в `LocalStorageManager` только два служебных ключа состояния -- `PREF_ANTI_SPY_BOOT_FREEZE_PENDING` и `PREF_ANTI_SPY_LAUNCH_VERSION_CODE`. Пользовательского переключателя не существует, поведение зашито намертво.

## Почему это дефект, а не мелочь

Замер на устройстве пользователя 10.08.2026 показал: **трафик рабочего профиля не идёт через VPN**, поднятый в личном профиле. Профиль -- отдельный пользователь со своей маршрутизацией, приложениям профиля адрес VPN недоступен.

Значит для такой конфигурации автозаморозка по поднятию VPN:

* не даёт **никакой** защиты -- скрывать нечего, приложения и так видят обычный адрес;
* при этом гасит приложения, то есть **убивает уведомления** от мессенджера, банков, госуслуг.

Пользователь платит потерей уведомлений за безопасность, которую не получает. И не может это отключить.

То же справедливо для любой схемы с раздельным туннелированием, где приложения профиля намеренно выведены из-под VPN.

## Требования

**Главный переключатель, по умолчанию выключено.** Функция меняет фоновое поведение системы и может стоить пользователю пропущенных сообщений -- включаться она должна осознанно.

**Раздельные триггеры.** Заморозка по поднятию VPN и заморозка по блокировке экрана -- разные сценарии, у каждого свой переключатель.

**Выбор области.** Что именно морозить: весь профиль, список автозаморозки, отдельный список для этого триггера. Не переиспользовать чужой список молча.

**Мягкий режим.** Вместо заморозки -- только уведомить, что VPN поднят при незамороженных приложениях. Для тех, кому важнее уведомления, чем автоматика.

**Задержка перед заморозкой** с возможностью отменить. Сейчас реакция мгновенная.

**Честный текст в настройках.** Прямо сказать, в каком случае функция бесполезна: если приложения рабочего профиля не маршрутизируются через VPN, замораживать их при подъёме VPN незачем.

**Подсказка по факту, а не по теории.** Приложение может проверить, идёт ли трафик профиля через туннель, и если нет -- сказать пользователю, что этот переключатель ему ничего не даст. Данные для проверки те же, что использует `VpnTunnelDetector`.

## Уведомление сервиса

Отдельным пунктом, из того же разбора.

`ensureForeground()` строит уведомление через `Utility.buildNotification(this, true, ...)`, где `true` означает важный канал: `IMPORTANCE_HIGH` плюс `enableVibration(true)`. Для служебного уведомления фонового сторожа это неверно -- оно звучит и всплывает поверх экрана. Требуется `IMPORTANCE_MIN`: иконка в шторке, без звука, без вибрации, без всплытия.

Отдельно убрать принудительное переписывание настроек канала при каждом вызове (`chan.importance = ...`, `enableVibration(...)`). Android после создания канала повышение важности приложению не даёт, так что фактически это не работает, но намерение перебить пользовательский выбор из кода недопустимо.

## Связанные дефекты того же сервиса

Из вердикта Фазы 1, требуют починки вместе с настройками:

* цикл перезапуска каждые 5 секунд: `SecurityException` при `startForeground` с типом `systemExempted` без требуемых разрешений (`AntiSpyVpnWatchService.kt:102`);
* `registerReceiver` без обязательного с API 34 флага экспорта (`:143`);
* утечка ресивера.
