# Аудит: Shelter (Java) и CoreGuard (Kotlin). Что дорабатывать

Цель: личное использование на **Oppo Find X9 Pro Global, ColorOS 16**. Дата: 10.08.2026.
Связанные документы: [4pda_compat_matrix.md](4pda_compat_matrix.md), [4pda_code_verification.md](4pda_code_verification.md), [android_modernization.md](android_modernization.md).

## 1. Твоя платформа: что известно из 142 постов по BBK

ColorOS/OxygenOS/RealmeUI -- одна кодовая база (Oppo/OnePlus/Realme). По форуму это **вторая по благополучности платформа после чистого AOSP**: 9 жалоб из 82 свежих, против 21 у Xiaomi.

Что работает:

* **Провижининг и профиль в целом.** #1617: "У меня ColorOS, рабочее пространство работает вполне корректно". Установка и заморозка -- #1006, #1007, #269, #1287.
* **Установка в профиль без плясок.** #1617: RuStore скачан в основном профиле, переброшен через боковое окно, открыт проводником в пространстве, установлен. MIUI-капитуляция тебя не касается -- гард `isMIUI()` на твоем устройстве не сработает.

Что сломано или требует обхода:

* **Отпечаток пальца для рабочего профиля.** В настройках ColorOS/OxygenOS пункта нет. Обход #1699: поставить Activity Launcher внутрь профиля, найти активность fingerprint, запустить, ввести пароль основного профиля, добавить отпечаток. Заявление того же поста, что "OnePlus/Oppo/Realme системно понизили рабочий профиль до уровня гостя", автор взял **из ответа Gemini** -- это не источник, проверять отдельно.
* **NFC-оплата из профиля.** #1872 (OnePlus 13s): Mir Pay в профиле карту добавляет и читает, но оплата не проходит -- ошибка 5001 либо терминал не читает. #1647 (Realme GT 7 Pro): выставить Mir Pay по умолчанию дает, но при отключении Shelter слетает весь модуль NFC. Вывод поста: "технически это очень плохая идея".
* **Android 16.** Твоя ColorOS 16 -- это A16. Значит на тебя ложатся: краш ярлыка общей заморозки (#1706, причина не установлена), выборочная автозаморозка (#2083, OnePlus 8 на A16), `adb pm uninstall --user N` с `SecurityException` (#2072).
* **Автозапуск.** BBK агрессивно душит фон. Для автозаморозки по блокировке экрана Shelter держит процесс в профиле уведомлением -- на ColorOS это первый кандидат на отстрел. Проверять руками.

**Прогноз:** база заведется почти наверняка. Дорабатывать придется A16-специфику и мелочи ColorOS, а не бороться с прошивкой.

## 2. Аудит Shelter

### 2.1 Архитектура

5 186 LOC, 25 файлов, Java, Views + XML. Модель: **два экземпляра одного APK** -- в основном профиле и в рабочем -- общаются через AIDL-биндер.

```
MainActivity (основной профиль)
   │  bindService через Utility.transferIntentToProfile
   ▼
DummyActivity (экспортирован, точка входа кросс-профильных запросов)
   │  проверка подписи → маршрутизация
   ▼
ShelterService (AIDL, BIND_DEVICE_ADMIN) ── клонирование, заморозка, иконки
FileShuttleService (AIDL) ── файловые операции
CrossProfileDocumentsProvider ── SAF-фасад, выключен по умолчанию
FreezeService ── заморозка по блокировке экрана
ShelterDeviceAdminReceiver ── Profile Owner
```

Ядро аккуратное. Разделение сервисов честное, AIDL-границы понятные. Вся сложность проекта -- в кросс-профильном IPC, и она обоснована: другого способа нет, `INTERACT_ACROSS_PROFILES` для нас закрыт.

### 2.2 Безопасность: четыре находки

Граница доверия -- `DummyActivity`, `AndroidManifest.xml:65`: `android:exported="true"` **без `android:permission`**. Через нее проходят `INSTALL_PACKAGE`, `UNINSTALL_PACKAGE`, `FREEZE_ALL_IN_LIST`, `UNFREEZE_AND_LAUNCH`, `START_FILE_SHUTTLE`. Защита -- HMAC-подпись интентов плюс два списка исключений.

**S1. Бутстрап ключа доверяет первому встречному.** `util/AuthenticationUtility.java:41-46`:

```java
if (key == null) {
    if (intent.hasExtra("auth_key")) {
        LocalStorageManager.getInstance().setString(
                LocalStorageManager.PREF_AUTH_KEY, intent.getStringExtra("auth_key"));
        return true;
```

Пока локальный ключ не установлен, **любое приложение может прислать свой `auth_key` в экспортированную activity, пройти проверку и навсегда посадить общий секрет, который оно знает**. Дальше все его интенты подписаны валидно. Окно -- до первой установки ключа: свежий профиль сразу после провижининга и любой вызов `AuthenticationUtility.reset()`. Комментарий в `DummyActivity.java:170` это осознает ("ONLY the first received one should be stored and trusted"), но защиты от гонки нет.

**S2. Подпись не покрывает ни action, ни параметры.** `util/AuthenticationUtility.java:64-70` -- `sign(key, timestamp)` считает HMAC **только от таймстампа**. Валидная подпись для безобидного интента авторизует любое другое действие в пределах окна. Это токен предъявления, а не контроль целостности.

**S3. У окна нет верхней границы.** `util/AuthenticationUtility.java:52-54`:

```java
return timestamp - intentTimestamp < 30 * 1000 &&
        sign(key, intentTimestamp).equals(intent.getStringExtra("signature"));
```

Если `intentTimestamp` **в будущем**, разность отрицательна, условие истинно. Подпись с таймстампом на год вперед не протухает никогда. Само по себе требует знания ключа, но в связке с S1 превращает разовый захват в постоянный доступ.

**S4. Флаг `is_same_process` -- обычный extra интента.** `ui/DummyActivity.java:109-121`. `registerSameProcessRequest` кладет `intent.putExtra("is_same_process", true)` и запоминает время в статике. `checkSameProcessRequest` читает этот extra из **входящего** интента. Поскольку activity экспортирована, внешнее приложение может выставить тот же extra само. Единственный барьер -- попасть в 5-секундное окно после легитимной регистрации. Спамящий интентами атакующий и попадет, и **заберет токен себе**: успешная проверка выполняет `sLastSameProcessRequest = -1`, то есть легитимное действие после этого сломается. Открывает `INSTALL_PACKAGE`, `UNINSTALL_PACKAGE`, `UNFREEZE_AND_LAUNCH`.

**Насколько это практично.** Все четыре -- анализ кода, не эксплуатация: PoC я не писал, на устройстве не проверял. Но модель угроз здесь не абстрактная. Смысл приложения -- изолировать враждебный софт, и этот софт живет **внутри рабочего профиля**, где `DummyActivity` экспортирована и доступна. То есть ровно тот, от кого защищаются, находится по нужную сторону границы. Для личного использования на своем устройстве это низкий риск. Для продукта -- чинить до релиза.

### 2.3 Готовность к Android 16

| Пункт | Состояние |
|---|---|
| targetSdk релиза 1.9.1 | 34. master -- 35. Нужен 36 |
| Edge-to-edge | Не сделан. На targetSdk 36 отказ невозможен, править всю верстку Views/XML |
| Predictive back | Не сделан. `onBackPressed()` перестанет вызываться |
| Monochrome-иконка | Нет у `ic_freeze`. С A16 QPR2 система темизирует сама, будет криво |
| Хендлеры провижининга | `GET_PROVISIONING_MODE` / `ADMIN_POLICY_COMPLIANCE` отсутствуют, идет старым путем через `ACTION_PROVISIONING_SUCCESSFUL` (`AndroidManifest.xml:88-100`). Риск, не подтвержден |
| Квоты фоновых задач | Пересчитаны по standby bucket -- бьет по автозаморозке на `AlarmManager` |

### 2.4 Техдолг

* Вендоренная в репозиторий `libs/SetupWizardLibrary` -- мертвая гугловская библиотека, тянется с 2018.
* Пустые `catch` в UI-слое: `AppListFragment.java:373` и рядом -- `catch (RemoteException e) {}` без обработки. Отвалившийся биндер молча превращается в "ничего не произошло".
* `DummyActivity` -- диспетчер на 15 действий в одном классе.
* Тестов нет: `ExampleUnitTest`, `ExampleInstrumentedTest` -- шаблоны из IDE.
* `Utility.isMIUI()` дергает `getprop` в дочернем процессе на каждый вызов, синхронно.

## 3. Аудит CoreGuard

### 3.1 Что это

4 181 LOC, 18 файлов, Kotlin 100%, `targetSdk 36`, `minSdk 26`, Views + viewBinding.

**Другая архитектура, потому что другая задача.** CoreGuard не делает кросс-профильных операций вообще. Он ставится Profile Owner и применяет политики DPM. Отсюда экспортированная поверхность в три компонента (`MainActivity`, алиас `MainActivityLauncher`, `AppDeviceAdminReceiver` под `BIND_DEVICE_ADMIN`), ноль AIDL, ноль собственной криптографии -- и ноль проблем класса S1-S4.

Цена: **нет клонирования приложений и нет переноса файлов**. Ни `PackageInstaller`, ни `DocumentsProvider` -- проверено грепом, пусто. Только `enableSystemApp` для системных (`AddAppsActivity.kt:156`).

### 3.2 Что у него есть ценного

Богатая обвязка DPM, которой нет у Shelter, -- `admin/ProfileManager.kt`, 499 строк:

`setWorkProfileScreenCaptureDisabled`, `setClipboardSharing`, `setContactsSharing`, `setIntentSharing`, `denyPackageEnumerationToManagedApps`, `restrictPhoneStatePermission`, `clearWorkProfileVpn`, `setBluetoothSharingRestricted`, `setNfcBeamRestricted`, `setUninstallBlockedForAllApps`, `hideLauncherIcon`, per-app оверрайды разрешений (`AppPermOverride.kt`, `applyPermissionsForNewApp`).

Плюс движок триггеров: `TriggerMonitorService.kt` (606 строк), `TriggerEvaluator.kt`, `TriggerConfig.kt`, `NetworkState.kt` -- автоматика по состоянию сети и загрузке, а не только по блокировке экрана.

Это самодостаточные вызовы. Переносятся по одному.

### 3.3 Качество кода

Хуже, чем у Shelter, несмотря на более свежий язык.

* **Логика в activity, слоев нет.** Ни `ViewModel`, ни `LiveData`, ни `StateFlow` -- ни одного вхождения. `SettingsActivity.kt` -- 822 строки, `MainActivity.kt` -- 604, `TriggerMonitorService.kt` -- 606. Корутины запускаются прямо из `lifecycleScope` в activity.
* **54 блока `catch` на 4 181 строку** -- один на 77 строк. Девять из них глушат исключение молча, например `MainActivity.kt:557`: `catch (_: Exception) { emptyList() }`. Различить "нет данных" и "сломалось" невозможно.
* Тестов нет.

### 3.4 Риски происхождения

* **4 коммита на всю историю** при 4 181 LOC. История сквошена, откуда взялся код -- непроверяемо. Для приложения с правами Profile Owner это существенно: диффа, который можно прочитать, не существует.
* **Пароль релизного keystore лежит открытым** в `app/build.gradle.kts`: `storePassword = "CoreGuard_store_2026"`, `keyPassword` тот же. Сам `.jks` не закоммичен -- `git ls-files` по `*.jks`/`*.keystore` пусто, проверил. Подписать чужую сборку сейчас нельзя. Но пароль в VCS означает, что утечка файла ключа сразу означает утечку подписи.
* Тему CoreGuard на 4PDA забанили (#1800), дистрибуция только GitHub.

**Вывод по CoreGuard: как база -- нет, как донор DPM-вызовов -- да.** Перед заимствованием прочитать каждый переносимый метод глазами, а не копировать блоками.

## 4. Что дорабатывать. Для себя, по порядку

Порядок такой, что каждый следующий шаг имеет смысл только если предыдущий прошел.

**Шаг 0. Проверить, что вообще заводится на ColorOS 16.**
Собрать master Shelter как есть, поставить, поднять профиль. Это проверяет главный невыясненный риск -- работает ли старый путь провижининга на Android 16 без `GET_PROVISIONING_MODE`/`ADMIN_POLICY_COMPLIANCE`. Если нет -- все остальное неважно, сначала переписывать провижининг. По форуму на A16 профиль поднимается, но на BBK+A16 подтверждений нет.

**Шаг 1. Поймать краш ярлыка общей заморозки.**
У тебя A16 -- воспроизведешь. Нужен `logcat` в момент нажатия "создать ярлык общей заморозки". Гипотеза (adaptive-icon через `Icon.createWithResource`, `MainActivity.java:411`) документацией **не подтверждается**: известная проблема визуальная, не краш. Без стектрейса чинить нечего.

**Шаг 2. Базовая пригодность на своей прошивке.**
Проверить и починить по факту: автозаморозка по блокировке экрана переживает энергосбережение ColorOS; уведомление, которым Shelter держит процесс в профиле, не отстреливается; отпечаток добавляется трюком #1699 или нет.

**Шаг 3. targetSdk 36.**
Edge-to-edge, predictive back, monochrome-слой для `ic_freeze`. Механическая работа, но по всем экранам.

**Шаг 4. Перенести из CoreGuard то, что реально нужно.**
Для твоей задачи первые кандидаты: `setWorkProfileScreenCaptureDisabled`, `setClipboardSharing`, `denyPackageEnumerationToManagedApps`, `setIntentSharing`. Каждый -- один вызов DPM, читается за минуту.

**Шаг 5. Kotlin.**
Не раньше. Миграция ради миграции на работающей базе -- риск без выгоды. Начинать с листьев (`util/`), не с `DummyActivity`.

**Что не делать.**

* Не гнаться за сокрытием VPN. `tun0` виден из профиля, это стена платформы. 129 постов форума об это разбились.
* Не рассчитывать на NFC из профиля. Новые API A16 доступны только Device Owner и корпоративным профилям, BYOD -- нет. На BBK вдобавок #1647: отключение Shelter роняет модуль NFC целиком.
* Не чинить MIUI. Не твоя платформа.

**Для продукта, но не для себя:** S1-S4 из раздела 2.2. На своем устройстве, где ты контролируешь что стоит, риск низкий. В публичном релизе -- чинить до, а не после.
