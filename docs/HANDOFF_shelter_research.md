## 2. Контекст РФ / РКН (драйверы спроса) — проверенные факты

- **MAX (госмессенджер) — обязательная предустановка с 1 сентября 2025.** ~63 запрашиваемых
  разрешения (в т.ч. камера, микрофон, геолокация, Bluetooth). Штатно удаляется не везде.
  Массово воспринимается как «шпион». → прямой триггер «заморозить/изолировать».
- **RuStore — обязателен по закону** (принят июнь 2025, действует с 1 сентября 2025) на всех
  Android; попытка затащить и на iOS. Штатно неудаляем.
- **Закон о штрафах за поиск «экстремистских материалов» и за рекламу VPN — подписан 31.07.2025.**
  → убивает легальную монетизацию всего, что пахнет «обходом», внутри РФ.
- **Блокировка VPN-протоколов дошла до VLESS** (душат с ~декабря 2025, усилили февраль 2026),
  плюс SOCKS5. Раньше VLESS/Reality считался «неубиваемым».
- **Отключения мобильного интернета + «белые списки»** (Госуслуги, VK, MAX, RuStore, Яндекс…) —
  регулярная практика 2025–2026.
- **«Частичное ограничение звонков» в WhatsApp/Telegram — с августа 2025.**

Вывод: спрос на изоляцию в РФ вырос, но сместился с «спрятать личное» на **«локализовать
навязанное гос-ПО + развести трафик»**.

## 3. Механика Android — 4 механизма изоляции, что умеют и где стены

### 3.1 Work profile (рабочий профиль) — на нём построен Shelter
- Отдельный Android-**пользователь** (managed profile) под основным: свой `/data/user/10/`, своё
  шифрование, **свой диапазон UID**. Приложение (Shelter) = **Profile Owner (DPO)**, рулит через
  `DevicePolicyManager`.
- Изоляция **настоящая, на уровне ядра** (UID+SELinux): приложение в профиле не видит и не может
  сделать IPC с приложением в личном. Сильнее, чем «клоны» (Parallel Space/Island God-mode/Xposed).
- Инструментарий DPO: заморозка `setApplicationHidden()` / `setPackagesSuspended()`; отдельный VPN
  только на профиль `setAlwaysOnVpnPackage()`; отзыв разрешений; политика cross-profile;
  мост интентов `addCrossProfileIntentFilter()`; API `CrossProfileApps` (API 30+).
- **Ограничения (важно):**
  1. **Один** work profile на устройство.
  2. **Нельзя изолировать предустановленное СИСТЕМНОЕ приложение** (MAX/RuStore, если зашиты в
     прошивку) — Profile Owner их не трогает, они живут в основном пользователе.
  3. Провижининг сужается каждый год; Google режет DeviceAdmin/DPM. На Android 15/16 надо
     проверять руками, что self-provisioning без EMM жив и target SDK 34/35 собирается.
  4. Приложение в профиле знает, что оно в профиле, и видит VPN.
  5. Двойной ресурс/батарея/каша уведомлений.

### 3.2 Private Space (Android 15+) — нативный конкурент
- «Work profile для физлиц» от Google. Отдельный аккаунт/Play, автолок, скрыт по умолчанию.
- **Дыры под РФ-задачу:** трафик Private Space **байпасит VPN** (дисквалификация для обхода DPI);
  **нет freeze**; не прячет по-настоящему (виден через package viewer); нет backup/restore.
- Privacy Guides уже рекомендует Private Space вместо Shelter на Android 15+ → отъедает базовый
  сценарий Shelter, но **не** закрывает РФ-кейс (изоляция гос-ПО + разведение трафика).

### 3.3 Secondary user (несколько пользователей устройства) — самый сильный по изоляции
- Полноценный отдельный пользователь: всё своё, взаимно невидимы, **моста между ними нет вообще**.
- **Против продукта:** (1) стороннее приложение **не может** создавать/переключать юзеров —
  `CREATE_USERS`/`MANAGE_USERS` это `signature|privileged`, только система или **Device Owner**;
  (2) **нет одновременной работы** — переключение как logout/login, фоновый юзер встаёт (нет
  уведомлений/синка); (3) OEM часто режут multi-user на телефонах (Samsung/Xiaomi); (4) шаринг
  между юзерами **хуже**, чем у work profile — санкционированного моста нет вовсе.
- Плюсы: максимальная изоляция для «бёрнера»; guest/ephemeral user для одноразового.

### 3.4 Device Owner (+ multi-user / suspend) — «power»-путь
- Если приложение = **Device Owner** (владелец всего устройства; ставится на чистое/сброшенное
  устройство через `dpm set-device-owner` или QR, без аккаунтов), получает `MANAGE_USERS` →
  может создавать/переключать юзеров **И** глушить/выключать приложения в основном пользователе,
  **включая предустановленный системный MAX/RuStore**.
- Это **единственный чистый (без Shizuku/рута) путь** убить системный навязанный софт.
- Цена: **факторный сброс** + отсутствие аккаунтов при провижининге; **один** Device Owner;
  приложение фактически становится MDM устройства. Барьер высокий, но не рут.

### Карта
| Механизм | Изоляция | Одновременная работа | Управляется твоим app | Трогает системный MAX/RuStore | Барьер юзера |
|---|---|---|---|---|---|
| Work profile (Profile Owner) | настоящая | да | да | **нет** | низкий |
| Private Space (A15) | настоящая | да | нет (нативка Google) | нет | низкий |
| Secondary user (обычный app) | максимальная | **нет** | **нет** | нет | средний/OEM |
| Device Owner (+multi/suspend) | максимальная | зависит | да | **да** | высокий (сброс) |

**Развилка, которую надо решить осознанно:** «изолировать всё» + «понятно юзеру» конфликтуют.
Чистый work profile НЕ возьмёт предустановленный системный MAX; Shizuku/Device Owner берут, но
ломают простоту. Варианты: (а) сузить «всё» до **user-installed** недоверенного софта (work profile
идеален); (б) **гибрид** — work profile для повседневной изоляции + опциональный Device Owner
(COPE-конфиг: Device Owner + work profile сверху) для тех, кому надо гасить системный шпионский софт.

## 4. Конкуренты (три репозитория) — фичи, что добавили, чего не хватает

### 4.1 anubis — github.com/sogonov/anubis  (СИЛЬНЕЙШИЙ)
- Kotlin/Compose, ~1.2k звёзд, живой (v0.1.5.1, май 2026).
- **НЕ work profile.** Использует **Shizuku** (мост с правами уровня ADB без рута) + `pm disable-user`

- Фичи: группы приложений с сетевыми политиками (Local / VPN Only / Launch-with-VPN); свой лаунчер
  с серыми иконками; оркестрация VPN-клиентов (v2rayNG, NekoBox, Clash Meta, WireGuard); детект VPN

- **Минусы:** это **не изоляция** (нет отдельного UID/хранилища/клонов) — просто вкл/выкл + VPN-гейт.
  **Shizuku — барьер** для обычного юзера (на не-рут телефоне переактивация через ADB после каждой
  перезагрузки). Ломает требование «максимально понятно».

### 4.2 zindan — github.com/GiorgioVik/zindan
- **Прямой форк Shelter.** Java 66% + Kotlin, v1.5.3 (июнь 2026), ~2 звезды.
- Добавлено поверх Shelter: русский UX/брендинг, «Anti-Spy VPN» (детект VPN → предложение
  заморозить), тосты сверху, тестирование на Samsung. По сути — косметика + VPN-триггер.
- **Чего не хватает:** архитектурно это Shelter → **та же проблема со скриншотами/шарингом**,
  он её не трогал. Преимущества по сути нет, кроме локализации.

### 4.3 CoreGuard — github.com/rastenieProfile/CoreGuard  (ближайший ориентир по фичам)
- Kotlin, API 26+, MIT, ~4 коммита (ранняя стадия).
- Добавлено поверх Shelter: **автозаморозка по триггерам** (VPN, Wi-Fi SSID, мобильная сеть,
  оператор); **Network Kill Switch** (локальный TUN-фаервол — пустой VPN-интерфейс в профиле глушит
  весь трафик); **пофичные ограничения разрешений** (гео/камера/микрофон); контроль буфера/контактов
  между профилями. Использует `setPackagesSuspended()`.
- **Чего не хватает:** незрелость; корпоративное позиционирование; про решение шаринга/скриншотов —
  ни слова. Бери как reference-архитектуру, не как серьёзного конкурента.

### Общий вывод по нише
Все конвергируют в «work profile / disable + VPN-триггерная заморозка для анти-слежки в РФ».
**Никто не закрыл три клетки:** (1) cross-profile шаринг файлов/скриншотов; (2) онбординг для

## 5. Корень проблемы Shelter со скриншотами/шарингом (это ключевой дифференциатор продукта)

Два РАЗНЫХ бага, их путают:

### Баг A — «не могу сделать скриншот приложения в профиле» (захват экрана)
Причина: DPO может выставить `setScreenCaptureDisabled(true)`; плюс OEM-политики (Samsung Knox для
work profile) и `FLAG_SECURE` самих приложений блокируют захват → «Не удалось сделать скриншот из-за
политики безопасности». **Фикс в продукте:** НЕ вызывать `setScreenCaptureDisabled(true)`, вынести
отдельным тумблером.

### Баг B — «криво шарятся файлы/скриншоты между профилями» (обмен) — ОСНОВНАЯ БОЛЬ
Механизм: граница профилей пропускает **только интенты** через системный `IntentForwarderActivity`.
Когда шаришь скриншот из личного в приложение рабочего профиля:
- Скриншот приходит как `content://`-Uri (MediaStore или FileProvider).
- Систему надо пере-выдать грант на Uri в другой user (`grantUriPermission` cross-user). Она делает
  это **только для одиночного, правильно помеченного** (`FLAG_GRANT_READ_URI_PERMISSION`) Uri.
- **Мультишаринг** (`ACTION_SEND_MULTIPLE` + ClipData) теряет гранты на все, кроме первого →
  подтверждённый баг: из N файлов сохраняется один (AmazeFileManager issue #2651).
- Приложения, отдающие legacy `file://`-Uri, через границу дают **пустоту** (путь указывает в чужой
  `/data`).
- Shelter прикрутил «FileShuttle» — свой ContentProvider, копирующий байты во временную область. Он
  течёт: temp-копия, ломает метаданные, мультифайл и стриминг.

**Как правильно решить (тех. ТЗ на фикс):**
- Свой **cross-profile ContentProvider** со **стримингом** через `openFile()`/`ParcelFileDescriptor`
  (а не temp-копия).
- Корректная обработка `ACTION_SEND_MULTIPLE`/ClipData: пере-грант **каждого** Uri по отдельности в
  целевой user.
- Собственный «мост галереи/файлов»: скриншоты личного профиля видны в пикере рабочего напрямую,
  без пляски интентов.
- Явная кнопка «отправить в рабочий профиль» через `CrossProfileApps` (API 30+), материализующая
  файл в grant-safe место и отдающая валидный content-Uri.
- Отдельно — не глушить захват экрана (Баг A).

## 6. Что строить — выводы и «что делать завтра»

### Позиционирование
Три незанятые клетки (см. 4): изоляция **user-installed** недоверенного софта + человеческий
онбординг + **работающий шаринг файлов/скриншотов**. Вокруг шаринга и продавать.

### Честная оценка (дыры первыми)
- «Ещё один Shelter-клон» — нет: нативка (Private Space) сверху + мёртвый апстрим Shelter (последний
  релиз 1.9.1, дек 2023) + гиковская узость.
- Реальный тех-смысл — «изоляция гос-ПО + per-profile обход DPI», но по монетизации бьёт закон
  31.07.2025 (реклама обхода запрещена в РФ) → это не бизнес внутри РФ-легала, а opensource/донат/
  комьюнити, возможно юрлицо вне РФ. Рычаг тут репутационный, не денежный.

### MVP-требования
1. База — форк **CoreGuard** (ближе всех: Kotlin, work profile + триггеры + suspend) или Insular;
   поднять target SDK 34/35, проверить на Android 15/16.
2. Понятный онбординг: мастер в 3 шага (создать профиль → выбрать «что спрятать» → включить
   VPN-профиль). Без Shizuku в базовом сценарии.
3. **Фикс шаринга** (раздел 5, Баг B) — главный дифференциатор.
4. **Фикс скриншотов** — не выключать `setScreenCaptureDisabled`.
5. Заморозка в один тап + автозаморозка по VPN/экрану (стандарт де-факто, как zindan/CoreGuard).
6. Опциональный Device Owner ИЛИ Shizuku-режим для системного MAX/RuStore — честно помечен «для
   продвинутых».

### Что делать завтра (по порядку)
1. **Проверить на реальном Android 15 и 16** (Pixel + Samsung отдельно): ставится ли self-owned
   work profile (`PROVISION_MANAGED_PROFILE`), работает ли `setAlwaysOnVpnPackage` на профиль, жив
   ли `addCrossProfileIntentFilter`. Бинарный gate всего проекта.
2. **Воспроизвести Баг B руками:** шарни 1 и N скриншотов личное→рабочее через Shelter, logcat →
   `grantUriPermission`/`SecurityException`. Подтвердить, что корень — потеря Uri-грантов на мульти.
3. **Прототип cross-profile ContentProvider** со стримингом и по-Uri грантами; тест на мультискрине.
4. Собрать CoreGuard/Insular под свежий SDK, проверить, что не падает на 15/16.
5. Решить рамку «изолировать всё»: user-installed only (чистый work profile) vs гибрид с Device
   Owner/Shizuku. От этого зависит весь онбординг.

### Данные, которых не хватает (не гадать — проверить)
- Жив ли self-provisioning work profile на РФ-прошивках (Xiaomi HyperOS, Samsung One UI 7/8) —
  замер руками.
- MAX/RuStore на целевых устройствах зашиты как **системные** (прошивка) или обычные apk — если
  системные, work profile их не изолирует в принципе (нужен Device Owner/Shizuku).
- Цель: комьюнити-проект или продукт (монетизация упирается в закон 31.07.2025).

## 7. ЗАДАЧА ДЛЯ CLAUDE CODE (локально): спарсить 4pda и вернуть структуру

### 7.1 Почему локально
4pda за Cloudflare, из облака 403. Твоя залогиненная сессия CF проходит. Голый Go/`http.Client`
тоже 403-нется (CF отдаёт JS-челлендж) — нужен **реальный headed-браузер**, где ты один раз
проходишь CF, дальше он держит `cf_clearance` cookie.

### 7.2 Скрипт-дампер (готов; лежит рядом: scrape_4pda.py)
Playwright + headed Chromium + persistent context. Логика:
1. `pip install playwright && playwright install chromium`, запуск `python scrape_4pda.py`.
2. Открывается окно → руками проходишь Cloudflare/логин → Enter в терминале.
3. Скрипт сам определяет число страниц по пагинации и сохраняет `dump/page_00000.html …`.
Параметры вверху файла: TOPIC=917380, STEP=20, DELAY_S=4.0 (если CF душит — подними до 8–10).
Ключевые моменты: `headless=False` (важно, иначе CF режет); `user_data_dir="./pw-profile"` держит
куки между запусками; есть проверка на «Just a moment»/`cf-challenge` с паузой на ручное прохождение.

### 7.3 Что распарсить из dump/*.html и вернуть
Селекторы 4pda (проверить на месте, вёрстка форума): тело поста обычно `.postcolor`; контейнер
поста — блок с автором/датой/номером. Из каждого поста тянуть: автора, дату, номер поста, текст;
device/OEM/Android-версию (по тексту), тип проблемы, воркэраунд.

Выходные артефакты:
1. **Матрица совместимости** (CSV/MD): устройство/OEM → прошивка/Android → работает? → примечание.
2. **Каталог багов + фиксов**, с приоритетом на скриншоты (Баг A) и cross-profile шаринг (Баг B) —
   собрать все упоминания, воркэраунды, различия по OEM (Samsung/Xiaomi/Pixel/GSI/кастомы).
3. **Гайды**: установка, миграция профиля, заморозка, отдельный VPN на профиль, восстановление
   после слёта, специфика Android 14/15/16 и конкретных вендоров.
4. Отдельным блоком — всё про **provisioning failures** («не создаётся work profile»,
   «security policy prevents…», кастомы/GSI) — это gate из раздела 6.

### 7.4 Известные ориентиры для сверки (из открытых источников, до 4pda)
- Скриншоты в work profile режутся политикой/`FLAG_SECURE` (подтверждено на XDA).
- Мультишаринг теряет Uri-гранты (AmazeFileManager #2651).
- Provisioning падает на части кастомов/GSI (сборщики вырезают DPM); фикс — чистая переустановка ROM
  (/e/OS форум) либо «security policy prevents creation of managed device because of custom OS» (XDA).
- Xiaomi HyperOS/MIUI и Samsung One UI — исторически проблемные по work profile; детали добрать из 4pda.
