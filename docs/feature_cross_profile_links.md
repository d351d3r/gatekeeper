# Фича C2: перехват ссылок в рабочий профиль (cross-profile link rules)

4PDA #2060, #1624: «ссылки из личного профиля не открываются в приложениях
рабочего». Это ограничение Android: `ACTION_VIEW` разрешается внутри одного
профиля. Обход существует на уровне платформы — кросс-профильные
intent-фильтры DevicePolicyManager, которыми управляет владелец профиля.

## Механика

- Настройка: список доменных правил (например `.ru`, `.su`,
  `example.com`). Каждое правило покрывает домен и все его поддомены.
- Применение: Gatekeeper (Device Policy Controller рабочего профиля) вызывает
  `DevicePolicyManager.addCrossProfileIntentFilter(admin, filter,
  FLAG_PARENT_CAN_ACCESS_MANAGED)` для каждого правила. Фильтр:
  `ACTION_VIEW` + `DEFAULT` + `BROWSABLE`, схемы `http`/`https`,
  authority-паттерны `rule` и `*.rule`.
- Изменение набора — `clearCrossProfileIntentFilters(admin)` и повторное
  добавление всех оставшихся правил: точечного `removeCrossProfileIntentFilter`
  больше нет (исключён из SDK 34+). Применённый список хранится в хранилище
  рабочего профиля (`PREF_CROSS_PROFILE_LINK_RULES`), т.к. DPM не умеет
  перечислять добавленные фильтры.
- Система: ссылка из личного приложения, совпавшая с фильтром, попадает в
  резолвер рабочего профиля и открывается там браузером по умолчанию
  (например, Яндекс Браузером рабочего профиля) или системным выбором.

## Threat model / приватность

1. **Рабочий браузер узнаёт URL.** Всё, что открывается по правилу,
   проходит через приложения рабочего профиля — включая их аккаунты,
   синхронизацию истории и трекеры. Правило-TLD вроде `*.ru` перенаправит
   **все** .ru-ссылки из всех личных приложений (мессенджеры, почта).
   Пользователь должен понимать: рабочий браузер = потенциально наблюдаемая
   зона, если в нём чужие аккаунты.
2. **Обратного направления нет.** Фильтры добавляются только
   `FLAG_PARENT_CAN_ACCESS_MANAGED` (личный → рабочий). Рабочие ссылки в
   личный профиль не утекают.
3. **Отзыв полный.** Удаление профиля удаляет фильтры; отдельное удаление
   правила из списка снимает именно его фильтр.
4. **Секретов нет.** Правила — это домены, не данные; бэкап (C4) включает
   их как обычную строковую настройку.

## Ограничения платформы (честно)

- В рабочем профиле должен быть браузер, способный принять `http(s)` VIEW;
  иначе система покажет выбор или откроет обработчик личного профиля.
- Интенты с явно указанным пакетом/компонентом фильтр не перенаправляет.
- App Links с auto-verify в личном профиле могут перехватывать ссылку до
  кросс-профильного фильтра — поведение зависит от версии Android.
- Проверено ли на устройстве: требуется ручной прогон (D2/D3); вендорские
  прошивки могут игнорировать кросс-профильные фильтры.

## Архитектура

- `util/CrossProfileLinkRules.kt` — чистая логика: нормализация ввода
  (scheme/path/port/регистр/точки), разбор списка, host-паттерны.
  Покрыта unit-тестами.
- `IGatekeeperService.setCrossProfileLinkRules(List<String>)` — добавлено
  в конец AIDL (порядок транзакций стабилен).
- `GatekeeperService` — применяет дифф через DPM; только в профиле-владельце.
- `SettingsFragment` — `EditTextPreference` в категории «Взаимодействие»,
  нормализованное значение, счётчик отброшенных записей, итог через toast.
