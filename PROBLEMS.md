## Частично решено в 1.3.8

### Anti Spy: VPN + работающее приложение в work profile

**Статус:** полуавтоматический обход (без Shizuku)  
**Затронуто:** Gatekeeper 1.3.8+

**Было (1.3.7):** фоновый монитор видел VPN, но автозаморозка из `:vpnwatch` в work profile не доставлялась.

**Стало (1.3.8):** при VPN-up — короткий dummy-VPN (вытеснение туннеля ~500 мс), затем уведомление:
«Закройте приложение в work profile» → **Да** = групповая заморозка (как снежинка); **Нет** = ничего (VPN Gatekeeper не восстанавливает, приложения работают).

**Ограничения:**
- Gatekeeper **не убивает** процесс в work — пользователь закрывает приложение сам.
- Пока приложение не закрыто, оно может снова увидеть VPN (если клиент переподключился).
- «Нет» подавляет повторный запрос до отключения VPN.
- Без разрешения VPN у Gatekeeper dummy-цикл не снимает туннель — показывается диалог **«Нужен доступ к VPN»** или **«Не удалось прервать VPN»** (1.3.10: на экране, не в шторке), а не «Да / заморозить всё».

**Полная автозаморозка без участия пользователя** по-прежнему требует Shizuku или иной привилегированный путь.

## Отложено

### Galaxy Store — не клонируется

**Статус:** отложено (платформенное ограничение)  
**Затронуто:** Gatekeeper — платформенное поведение

**Симптом:** клонирование Galaxy Store из основного профиля в рабочий не работает (тихий отказ / сообщение о системном приложении). Play Store и остальные приложения клонируются нормально.

**Причина (предположительно):** пакет с флагом system, в work profile ещё не установлен; используется только `enableSystemApp()`, чего недостаточно для OEM-магазинов.

**В Gatekeeper:** логика `installApp` без изменений (экспериментальный фикс `needsPackageInstallerClone` откатан — давал краш).

**Пакет:** `com.sec.android.app.samsungapps`

**Когда вернёмся:**

- общее решение для system + не установлен в профиле (не хардкод Samsung);
- разбор `logcat`, если снова будет краш;
- запасной путь через `installApk` (как в Gatekeeper2).

## Отложено — баги после 185 (следующая итерация, не в 185)

**Статус:** зафиксировано при тесте / обсуждении, **не чинить в 185**

### 1. Сообщение «Все приложения заморожены» — внизу (шторка)

**Симптом:** после групповой заморозки текст «Все приложения в списке автозаморозки были успешно заморожены» появляется **внизу** в шторке (уведомление рабочего профиля, иконка с портфелем), тогда как остальные сообщения Anti Spy — **вверху**.

**Ожидание:** все пользовательские сообщения только **сверху** (toast ~6 с), без дублирующего уведомления в рабочем профиле.

**Направление фикса (черновик 187):** убрать `postVpnAutoFreezeSuccessAlert` при ручной/ярлыковой групповой заморозке; оставить только `showToastOnMainProfile`.

### 2. Стартовая групповая заморозка при загрузке

**Симптом:** после перезагрузки / открытия Gatekeeper срабатывает «Заморозить всё», даже когда **все уже заморожены**; показывается лишнее сообщение; возможно **прерывание VPN**.

**Ожидание:** при boot/первом запуске замораживать только **ещё не скрытые** приложения из списка; если менять нечего — тишина; не мешать Anti Spy VPN.

**Направление фикса (черновик 187):** считать только вновь замороженные; стартовая заморозка через **фон** (`runStartupFreeze`), не UI-цепочку `DummyActivity`.

### 3. Клонирование основной → рабочий: двойной «Установить приложение?»

**Симптом:** при «Клонировать в Gatekeeper» диалог подтверждения установки появляется **дважды**; иногда первый тап не срабатывает (блокировка запросом уведомлений в рабочем профиле).

**Ожидание:** один диалог или **без диалога** (через `installExistingPackage` на API 28+).

**Направление фикса (черновик 190):** `installExistingPackage` + guard `PENDING_USER_ACTION` + не блокировать install запросом POST_NOTIFICATIONS.

### 4. Ярлыки групповых операций — пересоздать после 185

**Отложено — следующий цикл доработки (не чинить в 191):**

#### E-A. Первое включение VPN блокируется

**Симптом:** после разморозки тестовых приложений пользователь включает VPN — **первое** нажатие не подключает (блокируется); **второе** — VPN подключается.

**Вероятная связь:** реакция Anti Spy (`AntiSpyVpnWatchService` → `AntiSpyDummyVpnDisconnector`) на появление VPN пересекается с попыткой пользователя установить туннель.

#### E-B. Диалог «Заморозить всё?» при уже включённом VPN

**Симптом:** VPN уже работает → появляется запрос «Да, заморозить всё?» / «Нет».

**Ожидание пользователя:** при активном VPN — **сразу** групповая заморозка (как снежинка), **без** дополнительного диалога.

**Где сейчас:** `AntiSpyVpnWatchService.maybeFreezeAllForVpn()` → после dummy-displacement → `AntiSpyVpnPromptManager.showPrompt()` → `AntiSpyVpnPromptActivity` (Yes/No). «Да» → `PUBLIC_FREEZE_ALL`.

**Направление фикса:** при успешном displacement (или если displacement не нужен для фоновой заморозки) вызывать `AntiSpyManager.freezeAllForVpn(BACKGROUND)` напрямую, без `MODE_FREEZE_PROMPT`.

### Дополнение: work->parent CPIF не резолвится на AOSP 16 (блокирует фоновый отчет)

Механизм фонового автозамораживания (WorkPackageScanJobService + WorkPackageReportReceiver,
коммит с Фазами 1-3) упирается в платформенное ограничение эмулятора AOSP 16:
`queryIntentActivities` из процесса рабочего профиля НЕ возвращает системный форвардер
(`com.android.internal.app.ForwardIntentToManagedProfile`) ни для нового действия
`WORK_PACKAGES_REPORT`, ни для СТАРЫХ действий (`DELIVER_APP_LIST_REFRESH`), зарегистрированных
тем же `enforceWorkProfilePolicies` (проверено инструментальным зондом после явного вызова
enforce; candidates пустой). Направление parent->managed при этом работает.

Следствие: на этом стенде весь класс механизмов "рабочий профиль -> личный профиль через
CPIF" не доставляется (это касается и существующих фич, работавших в поле на Samsung).
Деградация новой функции = текущее поведение (автозаморозка при открытии списка приложений).
Джоба и ресивер корректны и заработают там, где CPIF работают (Samsung builds 231/235 --
полигон), либо после выяснения платформенных изменений AOSP 16 (кандидат: требования к
cross-profile visibility / access control).

### Решение по автозаморозке сторовых установок (сентябрь 2026)

Фоновый механизм автозамораживания сторовых установок (коммит `f11b9e9`:
`WorkPackageScanJobService` + `WorkPackageReportReceiver` + runtime-ресивер в
`GatekeeperService`) **откачен полностью**. Причины: манифест-ресивер `PACKAGE_ADDED` мёртв
на targetSdk 35, доставка work→parent через CPIF не резолвится на AOSP 16 -- на чистом
Android 16 механизм гарантированно деградировал до "сработает при открытии списка
приложений", при этом добавляя джобу, ресивер и подписанную кросс-профильную доставку.

Продуктовое решение: список автозаморозки **полностью ручной** -- приложение попадает в
него только явным включением снежинки пользователем (opt-out сохраняется и уважается всеми
триггерами заморозки). Сторовые установки по-прежнему появляются во вкладке "Рабочий" при
обновлении списка, пока Gatekeeper открыт.

### Честная оговорка про «ру серты»

корня не зависит.
