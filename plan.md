## Правила работы по каждому пункту

1. **Аудит** — сначала проверить фактическое поведение в коде Gatekeeper
   (не полагаться на то, что «должно работать»). Результат фиксируется
   одним из статусов: `OK` (работает, есть покрытие), `GAP` (работает,
   покрытия нет / покрытие слабое), `BUG` (воспроизводится или кодом
   подтверждено), `N/A` (платформенное ограничение — только документация).
2. Если `BUG` — чинить в отдельной ветке от `main`, минимальный дифф.
3. Каждый фикс — с тестами. Тип теста выбирается по слою:
   - чистая логика → JVM unit test (`app/src/test`, паттерн: `MiuiDetectorTest`,
     `AntiSpyWatchPolicyTest`, `VpnRoutingAdviceTest`);
   - работа с системой/profile APIs → инструментальный тест
     (`app/src/androidTest`, паттерн: `DocumentsProviderTest`,
     `AntiSpyVpnWatchTest`, AVD `gatekeeper_a16`);
   - то, что воспроизводится только на вендорских прошивках (MIUI/HyperOS,
     OneUI/Knox, ColorOS) → автоматизировать нельзя, оформляется как
     ручной сценарий в PROBLEMS.md + защитный код + unit-тест политики.
4. Зелёный CI (`lint → test → connectedCheck на AVD` если применимо → build)
   обязателен до мержа. Ничего не помечать «исправлено» без прогона.

## Блок A. Баги, унаследованные от апстрима (Shelter)

### A1. Установка APK внутри профиля на MIUI/HyperOS — «висяк» — P0

Симптомы: установка APK из профиля висит/«установщик не отвечает»,
кнопка «всё равно продолжить» ведёт в тупик (#2105, #2113, #867, #1046).
В апстриме дыра: гард `isMIUI()` есть только на одном пути, путь
`installApk` (через системный установщик) гарда не проходит; `isMIUI()`
читает `ro.miui.ui.version.name` через getprop и на HyperOS может
молча отвалиться (docs/4pda_code_verification.md).

- [x] Аудит (12.09.2026): **BUG подтверждён в Gatekeeper**. Гард MIUI есть
      только на пути клонирования (`AppListFragment:288`). Путь установки APK
      (`GatekeeperService.installApk` → `DummyActivity.actionInstallPackage`,
      строки ~266–324) гарда не проходил — ровно дыра апстрима. `MiuiDetector`
      читает `Build.MANUFACTURER/BRAND/DISPLAY` (надёжнее getprop-варианта
      апстрима, ловит xiaomi/redmi/poco и HyperOS по display).
- [x] Фикс: новый `InstallWarnPolicy` (предупреждать на MIUI только в
      рабочем профиле) + диалог в `DummyActivity` до запуска сессии установки;
      отмена отвечает вызывающему `RESULT_CANCELED` и чистит forward-proxy,
      вместо молчаливого висяка. Строки `miui_install_apk_warning` (en/ru).
- [x] Тесты: `InstallWarnPolicyTest` (JVM, 3 кейса: MIUI+work / MIUI+main /
      non-MIUI) — зелёные; `MiuiDetectorTest` — зелёный; `lintDebug` +
      полный `testDebugUnitTest` — зелёные.
- [ ] Ручной сценарий на реальном Xiaomi для PROBLEMS.md (нужен стенд).

### A4. Потеря/битое состояние профиля — нет пути восстановления — P1

(#2067: `IllegalStateException` трактуется как «профиля нет», флаг
`PREF_HAS_SETUP=false`, только пересоздание; #1404, #736, #751, #781 —

      резолва (`IllegalStateException`) больше не стирает флаг вслепую —

- [x] Фикс: перед мастером `init()` пробует существующий примитив

- [ ] Инструментальный/ручной сценарий на AVD: «профиль есть, флага нет»
      (подхват) и «профиль чужого DPC» (мастер с объяснением) — сессия

- [ ] Отдельно: диагностика бутлупа MIUI (#2069, Redmi 8, лечится
      удалением Shelter с профилем) — добавить в мастер проверку

      включать автозапуск профиля до завершения provisioning, логировать

### A8. Заморозка не гарантирует остановку процесса — P2, документация

(#2091 музыка играет после заморозки; Samsung Secure Folder ведёт себя

      VPN-watch). Force-stop пакетов недоступен profile owner ни одним API;
      доступен лишь `killBackgroundProcesses` (normal-разрешение), который не
      трогает foreground.
- [x] Фикс (best-effort): `WorkProfileBatchFreeze.freezePackage` перед
      скрытием зовёт `killBackgroundProcesses` (+ разрешение в манифесте).
      Foreground-сервисы (музыка) осознанно не убиваются — граница зафиксирована
      в PROBLEMS.md.
- [ ] Тесты: инструментальный «фоновый процесс убит, foreground жив» — в
      ручной сессии AVD.
- [ ] **ПЕРЕОТКРЫТО 13.09.2026: аудит был неверен.** Проверка на стенде
      (Android 16, AVD gatekeeper_a16) показала, что `setApplicationHidden`
      останавливает и приложение переднего плана:
      `am start --user 11 -n ru.oneme.app/one.me.android.MainActivity` →
      `topResumedActivity=... u11 ru.oneme.app`, `oom_score_adj=0`, после
      `pm hide --user 11` `pidof` пуст. Платформа делает force-stop, а музыка
      играет дальше из-за нашей же настройки `settings_dont_freeze_foreground`.
      Строка «Gatekeeper only kills background processes best-effort» в README,
      README_RU и USER_GUIDE §12 неверна и вводит в заблуждение.
      Что сделать: переписать формулировку (граница продукта, а не платформы),
      в сводке настройки честно сказать «музыка и звонки не прервутся, но
      приложение останется работать», и перепроверить, нужен ли вообще
      `killBackgroundProcesses` рядом со скрытием. Детали и команды —
      `.ai/ui-redesign/platform-walls-research.md`.

- [x] B3. Скриншоты: покрытие Media Mirror подтверждено (Pictures/Screenshots +

- [x] B5. adb-ограничения: задокументировано в README; рецепты «где лежит

      профиля не открываются в приложениях рабочего» и заменить его на реальное

      кросс-профильного фильтра, поведение зависит от версии Android.

### E-1. Galaxy Store не клонируется в рабочий профиль — фикс готов, ждёт проверки на железе

### E-2. Первое включение VPN блокируется — не воспроизводится, сценарий зафиксирован

- **Симптом (build 191):** первый тап «подключить VPN» не подключает, второй —
  подключает. Пересечение `AntiSpyVpnWatchService`/`AntiSpyDummyVpnDisconnector`
  с пользовательской попыткой поднять туннель.
- **Аудит (12.09.2026):** связка реагирования на VPN сторожа проходит через
  `AntiSpyDummyVpnDisconnector.isSuppressingVpnReactions()`; пересечение с
  пользовательским запросом возможно, только если suppress-флаг живёт дольше
  собственного отключения сторожа. На эмуляторе (API 36, без стороннего VPN)
  сценарий не воспроизводится — нужно железо с реальным VPN-клиентом.
- **Проверка на устройстве:** включить антишпион + заморозку по VPN, затем
  первым тапом подключить свой VPN. Если тап мимо — снять logcat
  (`AntiSpyVpnWatch`, `AntiSpyDummyVpn`, `VpnWatch`) и сериализовать
  disconnector/пользовательский запрос по suppress-флагу. До воспроизведения
  код не трогаем: слепая перестройка гонки опаснее наблюдения.

### E-6. Фоновая автозаморозка сторовых установок откачена — ограничение зафиксировано — P2

- **Факт:** `PACKAGE_ADDED` манифест-ресивер мёртв на targetSdk 35; доставка
  work→parent через CPIF не резолвится на AOSP 16 (на Samsung работала).
  Механизм `WorkPackageScanJobService`/`WorkPackageReportReceiver` откачен
  полностью (сентябрь 2026). Решение: список автозаморозки полностью ручной.
- **Остаток:** пакеты, установленные в профиль ДО первого открытия списка
  приложений, становятся базлайном и никогда не автозаморозятся (Gap).
  Кандидат доработки — JobScheduler-поллинг набора пакетов (без манифест-
  ресивера), приоритет низкий: текущее поведение осознанно принято.
- **ПЕРЕСМОТРЕНО 13.09.2026: фича воскрешаема, одно из двух обоснований неверно.**
  Про манифест-ресивер верно: `ACTION_PACKAGE_ADDED` отсутствует в списке
  исключений из ограничений фоновых рассылок (исключены только
  `ACTION_PACKAGE_DATA_CLEARED` и `ACTION_PACKAGE_FULLY_REMOVED`).
  Про CPIF — неверно, опровергнуто замером на том же AVD:
  `cmd package query-activities --user 11 -a io.gatekeeper.action.SHOW_TOAST`
  отдаёт `ForwardIntentToParent`, из user 0 `TRY_START_SERVICE` отдаёт
  `ForwardIntentToManagedProfile`. Работают оба направления; в августе, судя по
  всему, искали не тот псевдоним форвардера (из рабочего профиля система отдаёт
  ForwardIntentToParent, а не ForwardIntentToManagedProfile).
- **Чем заменить ресивер:** `PackageManager.getChangedPackages(sequenceNumber)`
  (API 26+) — та же модель догона по watermark, что уже работает в MediaMirror.
  При каждом подъёме службы рабочего профиля спросить изменения с последнего
  номера, новые пакеты добавить в список, личной стороне сообщить через реле.
  Это заодно закрывает «Остаток» выше: пакеты, поставленные до первого открытия
  списка, вернёт первый же вызов. Разбор — `.ai/ui-redesign/platform-walls-research.md`.

### E-7. MediaMirror: относительный путь молча клампится в корень — исправлено

- **Факт (Фаза 17):** `FileShuttleService.resolvePath` понимает только

### E-9. Системный выбор профиля вылезает поверх приложения — исправлено

Пользователь иногда получал системный диалог «Complete action using» с вкладками
Personal | Work и одним Gatekeeper в списке. Это не диалог приложения: так
Android спрашивает, в каком профиле выполнить действие, когда интент резолвится
в обоих.

Причина: действие `REFRESH_MAIN_APP_LIST` было зарегистрировано в
`RELAY_ACTION_FILTERS` в обе стороны. Рабочий профиль отправляет его через
системный форвардер, интент приезжает в личный — и там резолвится сразу в две
цели: своя `DummyActivity` (действие объявлено в манифесте) и форвардер обратно
в рабочий. Двусмысленный интент Android показывает пользователю.

Замер на AOSP 16 (эмулятор, переключение на вкладку рабочего профиля):
`START u11 {act=io.gatekeeper.action.REFRESH_MAIN_APP_LIST
cmp=android/com.android.internal.app.ResolverActivity}` и следом
`Displayed android/com.android.internal.app.ResolverActivity for user 11`.

Починка: у действия осталось одно направление (рабочий -> личный); личный
профиль его через реле не шлет, там компонент задается явно. После правки в
логе `cmp=android/com.android.internal.app.ForwardIntentToParent` и
`cmp=io.gatekeeper/.ui.DummyActivity`, `ResolverActivity` — ноль.

Тот же класс ошибки был у `REMOVE_UNFREEZE_SHORTCUT` (тоже обе стороны, и это
действие реально шлют оба профиля). Разведено на два действия по одному
направлению — тем же приемом, что `START_FILE_SHUTTLE` / `START_FILE_SHUTTLE_2`,
про который в манифесте давно висит комментарий «иначе будет диалог выбора».

Осталось: `AppListRefreshReceiver.ACTION` и `MainActivity.ACTION_REFRESH_APP_LISTS`
тоже зарегистрированы в обе стороны, но их отправители задают компонент явно в
своем же профиле, то есть обе регистрации мертвые. Не трогал: удаление требует
прогона всех путей обновления списка.
