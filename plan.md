# План: аудит и починка болей из темы 4PDA (Shelter, topic 917380)

Статус: черновик плана. Источники: `docs/4pda_*.md`, `docs/shelter_4pda_posts.json`
(2142 поста, дамп 10.08.2026). Номера `#NNNN` — посты темы.

## Правила работы по каждому пункту

1. **Аудит** — сначала проверить фактическое поведение в коде Gatekeeper
   (не полагаться на то, что «должно работать»). Результат фиксируется
   одним из статусов: `OK` (работает, есть покрытие), `GAP` (работает,
   покрытия нет / покрытие слабое), `BUG` (воспроизводится или кодом
   подтверждено), `N/A` (платформенное ограничение — только документация).
2. Если `BUG` — чинить в отдельной ветке от `main`, минимальный дифф.
3. Каждый фикс — с тестами. Тип теста выбирается по слою:
   - чистая логика → JVM unit test (`app/src/test`, паттерн: `MiuiDetectorTest`,
     `AntiSpyWatchPolicyTest`, `VpnRoutingAdviceTest`);
   - работа с системой/profile APIs → инструментальный тест
     (`app/src/androidTest`, паттерн: `DocumentsProviderTest`,
     `AntiSpyVpnWatchTest`, AVD `gatekeeper_a16`);
   - то, что воспроизводится только на вендорских прошивках (MIUI/HyperOS,
     OneUI/Knox, ColorOS) → автоматизировать нельзя, оформляется как
     ручной сценарий в PROBLEMS.md + защитный код + unit-тест политики.
4. Зелёный CI (`lint → test → connectedCheck на AVD` если применимо → build)
   обязателен до мержа. Ничего не помечать «исправлено» без прогона.

## Блок A. Баги, унаследованные от апстрима (Shelter)

### A1. Установка APK внутри профиля на MIUI/HyperOS — «висяк» — P0

Симптомы: установка APK из профиля висит/«установщик не отвечает»,
кнопка «всё равно продолжить» ведёт в тупик (#2105, #2113, #867, #1046).
В апстриме дыра: гард `isMIUI()` есть только на одном пути, путь
`installApk` (через системный установщик) гарда не проходит; `isMIUI()`
читает `ro.miui.ui.version.name` через getprop и на HyperOS может
молча отвалиться (docs/4pda_code_verification.md).

- [x] Аудит (12.09.2026): **BUG подтверждён в Gatekeeper**. Гард MIUI есть
      только на пути клонирования (`AppListFragment:288`). Путь установки APK
      (`GatekeeperService.installApk` → `DummyActivity.actionInstallPackage`,
      строки ~266–324) гарда не проходил — ровно дыра апстрима. `MiuiDetector`
      читает `Build.MANUFACTURER/BRAND/DISPLAY` (надёжнее getprop-варианта
      апстрима, ловит xiaomi/redmi/poco и HyperOS по display).
- [x] Фикс: новый `InstallWarnPolicy` (предупреждать на MIUI только в
      рабочем профиле) + диалог в `DummyActivity` до запуска сессии установки;
      отмена отвечает вызывающему `RESULT_CANCELED` и чистит forward-proxy,
      вместо молчаливого висяка. Строки `miui_install_apk_warning` (en/ru).
- [x] Тесты: `InstallWarnPolicyTest` (JVM, 3 кейса: MIUI+work / MIUI+main /
      non-MIUI) — зелёные; `MiuiDetectorTest` — зелёный; `lintDebug` +
      полный `testDebugUnitTest` — зелёные.
- [ ] Ручной сценарий на реальном Xiaomi для PROBLEMS.md (нужен стенд).

### A4. Потеря/битое состояние профиля — нет пути восстановления — P1

(#2067: `IllegalStateException` трактуется как «профиля нет», флаг
`PREF_HAS_SETUP=false`, только пересоздание; #1404, #736, #751, #781 —

- [x] Аудит (12.09.2026): часть дыр апстрима уже закрыта: транзиторный отказ
      резолва (`IllegalStateException`) больше не стирает флаг вслепую —
      `MainActivity.tryStartWorkService` проверяет `hasManagedProfile()` и
      показывает `WorkServiceBindFailure` с ретраем (покрыто

      существует», единственный выход — удаление профиля с потерей данных
      (#1404/#736/#781).
- [x] Фикс: перед мастером `init()` пробует существующий примитив
      `Utility.isWorkProfileAvailable()` — он подхватывает живой профиль,

- [ ] Инструментальный/ручной сценарий на AVD: «профиль есть, флага нет»
      (подхват) и «профиль чужого DPC» (мастер с объяснением) — сессия

- [ ] Отдельно: диагностика бутлупа MIUI (#2069, Redmi 8, лечится
      удалением Shelter с профилем) — добавить в мастер проверку
      «не переживёт ли устройство перезагрузку» нельзя, но можно: не
      включать автозапуск профиля до завершения provisioning, логировать

## Блок E. Открытые баги из PROBLEMS.md (перенесено 12.09.2026)

### E-1. Galaxy Store не клонируется в рабочий профиль — P1

- **Симптом:** `com.sec.android.app.samsungapps` (system, не установлен в
  профиле): `enableSystemApp()` тихо не отдаёт пакет; экспериментальный фикс
  `needsPackageInstallerClone` откатан (краш). Play Store и прочие клонируются.
- **План:** общее решение для «system + не установлен в профиле» без хардкода
  Samsung: кандидат `installExistingPackage` (API 28+) с guard
  `PENDING_USER_ACTION`; запасной путь — `installApk`. Разбор logcat при краше.
- **Проверка:** G3 подтверждён на build 191; после фикса — сценарий G3.

### E-2. Первое включение VPN блокируется — P1, нужна перепроверка

- **Симптом (build 191):** первый тап «подключить VPN» не подключает, второй —
  подключает. Пересечение `AntiSpyVpnWatchService`/`AntiSpyDummyVpnDisconnector`
  с пользовательской попыткой поднять туннель.
- **План:** перепроверить на текущем билде (1.5.3, builds 231+ меняли цикл
  опроса); если живо — сериализовать disconnector и пользовательский запрос.

### E-3. Toast «Все приложения заморожены» уходит в шторку рабочего профиля — P2

- **Симптом (после 185):** сообщение групповой заморозки появляется внизу,
  среди уведомлений рабочего профиля, а не toast сверху.
- **План:** убрать `postVpnAutoFreezeSuccessAlert` при ручной/ярлыковой
  групповой заморозке, оставить `showToastOnMainProfile`. Перепроверить,
  живо ли на текущем билде.

### E-4. Двойной диалог «Установить приложение?» при клонировании — P2

- **Симптом (185–191):** диалог подтверждения дважды; иногда первый тап мимо
  (блокировка запросом уведомлений рабочего профиля).
- **План:** `installExistingPackage` (API 28+) + guard `PENDING_USER_ACTION` +
  не блокировать install запросом POST_NOTIFICATIONS. Перепроверить на текущем.

### E-5. Стартовая групповая заморозка при загрузке — P2, не воспроизводится

- **Симптом (после 185):** лишнее «Заморозить всё» после reboot/первого
  запуска даже при всём замороженном. На Tab S9 FE+ (build 191, F3) **не
  воспроизведено**. Оставить как наблюдение; при воспроизведении — замораживать
  только не скрытые, стартовать из фона (`runStartupFreeze`).

### E-6. Фоновая автозаморозка сторовых установок откачена — ограничение зафиксировано — P2

- **Факт:** `PACKAGE_ADDED` манифест-ресивер мёртв на targetSdk 35; доставка
  work→parent через CPIF не резолвится на AOSP 16 (на Samsung работала).
  Механизм `WorkPackageScanJobService`/`WorkPackageReportReceiver` откачен
  полностью (сентябрь 2026). Решение: список автозаморозки полностью ручной.
- **Остаток:** пакеты, установленные в профиль ДО первого открытия списка
  приложений, становятся базлайном и никогда не автозаморозятся (Gap).
